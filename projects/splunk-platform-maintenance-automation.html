Platform Engineering Case Study / Production-used Windows upgrade automation

Splunk Platform Maintenance Automation

Production-used node-level Splunk Enterprise upgrade automation for Windows Server 2019, evolving toward topology-aware platform orchestration.

I built a Windows upgrade kit that performs the Splunk Enterprise upgrade itself rather than only printing commands. The common upgrade engine detects installed and target versions, validates the installer, backs up important Splunk state, runs the unattended MSI upgrade, restarts Splunk, and verifies the result.

The production workflow is run one node or component at a time. I decide which server runs next, while each local workflow applies role-specific checks, stops on mandatory failures, and records evidence for troubleshooting and recovery.

Problem

A Splunk upgrade needs more than an installer command.

Manual upgrades repeat the same high-risk steps: confirm versions, validate the installer, protect configuration and operational state, stop Splunk, run the MSI, recover the service, and verify that the upgraded role is healthy. The kit turns those steps into a repeatable node-level workflow while leaving platform-wide sequencing under operator control.

  • Different roles require different prechecks, restart behavior, and post-upgrade validation.
  • A disconnected RDP session must not interrupt an unattended upgrade.
  • A failed node must stop its workflow without losing recovery information.
  • Operators need detailed logs, MSI output, checkpoints, and a final summary.

Role Coverage

Dedicated wrappers share one common upgrade engine.

Management components

Cluster Manager, License Manager, Deployer, Deployment Server, and standalone variants use dedicated role-aware wrappers.

Cluster members

Search Head Cluster members and Indexer Cluster peers are upgraded individually, with health verified before the next node is started.

Forwarding tier

Heavy Forwarders use a dedicated workflow with service and relevant-port checks after the upgrade.

Current Workflow

Each node completes a controlled upgrade and verification cycle.

  1. Detect: identify the installed Splunk version and target version.
  2. Precheck: validate the installer and confirm the host is ready for upgrade.
  3. Protect: stop Splunk and back up important configuration and operational state.
  4. Upgrade: run the Windows MSI unattended and capture MSI output.
  5. Recover: restart Splunk, falling back to Windows Service Control if splunk.exe start fails.
  6. Verify: check service status, installed version, relevant ports, checkpoints, and final summary before the operator proceeds to the next node.

Safeguards and Recovery

Local failure handling is automated; platform progression remains operator-controlled.

Mandatory precheck or upgrade failures stop the individual server workflow. Warning-level findings can be explicitly overridden by the operator. Detailed logs, MSI logs, checkpoints, state information, and summaries preserve enough context for troubleshooting and recovery before the next component is started.

  • Version detection and installer validation
  • Configuration and operational-state backups
  • Unattended MSI execution
  • Scheduled Task support for RDP-disconnected sessions
  • Stop-on-failure behavior for mandatory local checks
  • Service, version, and relevant-port verification

Engineering Outcome

Node-level upgrade execution became repeatable and recoverable.

The kit moved Splunk Enterprise upgrades from a fragile sequence of manually repeated commands to a documented Windows workflow with backups, unattended installation, fallback service recovery, validation, and detailed evidence. I still control which platform component runs next, deliberately limiting blast radius during clustered maintenance.

This case study demonstrates production-used Windows upgrade automation, Splunk role awareness, failure containment, checkpoint-based recovery, and operational judgement.

Future direction: topology-aware orchestration is being designed separately. Planned capabilities include 8089-based coordination, automatic SHC and indexer-cluster health gates, indexer maintenance mode, platform-wide state tracking, resume-from-failure, a Splunk Web progress view, and an OS-neutral orchestration layer. These features are not represented as current production behavior.
